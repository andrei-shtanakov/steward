# Contract `approval-facts/v2` — merge-actor observations for the release gate

> Канон живёт здесь (steward — producer и владелец схемы). Потребители (dispatcher;
> позже другие читатели release-гейта) **вендорят пиненую копию** каталога и держат
> две раздельные гарантии: copy-integrity (offline PR-гейт) и upstream-drift
> (scheduled-наблюдение) — не одно `in_sync`. См. образец у `contracts/gate-verdicts/v1/`.
> Проектный документ: `docs/superpowers/specs/2026-08-21-approval-facts-v2-design.md`.

## Файл

`<repo-root>/.steward/approval_facts.jsonl` — рядом с `gate_verdicts.jsonl`, тот же
бандл, gitignored локальный артефакт. JSONL: одна запись на запрошенный элемент
scope, без искусственного SHA-ключа для отрицательных результатов, и malformed /
duplicate / missing / extra result изолируются на уровне отдельных строк фикстур.

## Записи (JSONL, по одной на строку)

Строка 1 — обязательно `header` и **только** первая строка; дальше — по одной
`result`-записи на каждый элемент `header.scope`. Нормативная схема —
`SCHEMA.json` (draft 2020-12, `additionalProperties: false` на каждой ветке:
«не требуется» означает **запрещено**, а не «необязательно»).

- **header** — заявка продюсера: `schema_version` (const `"2"`), `repository`
  (`owner/repo`), `generated_at` / `valid_until` (единая каноническая форма
  провода — см. ниже), `policy_version` / `policy_digest` (значение и sha256
  сырых байтов
  `profiles/approval-policy.yaml`), `complete` (const `true` — заявление, а не
  доказательство; читатель обязан проверить его сам через инварианты 3–5),
  `scope_sha256` и `scope` — типизированный список запросов `{kind, value}`.
- **result** — по одной записи на каждый элемент `scope`: `request` (эхо
  запрошенного `{kind, value}`), `state` (одно из пяти терминальных состояний
  ниже) и поля, обязательность которых зависит от `state` — см. матрицу.

`request.kind` — `pr` (`value`: целое ≥ 1) или `merge_sha` (`value`: 40-символьный
hex). Одно значение SHA может фигурировать в scope дважды под разными алиасами
(`pr:42` и `merge_sha:<oid>`, если они разрешаются в один и тот же мерж) — см.
инвариант 9.

## Пять терминальных состояний

| `state` | значение |
|---|---|
| `merged` | merge-событие существует, актор получен |
| `not_merged` | PR существует, `mergeCommit == null` |
| `not_found` | PR/commit доказанно отсутствует в доступном репозитории |
| `no_matching_pr` | commit существует, но не является merge-коммитом связанного PR |
| `actor_unavailable` | merge существует, но `mergedBy` отсутствует или неразрешим |

Классификация актора — **отдельное поле**, не состояние: `state: merged` с
доступным актором несёт `actor_class: human | agent | unknown`. «Классифицировано
как unknown» — это `state: merged` + `actor_class: unknown`, а не шестое
состояние.

### Матрица полей по `state`

`additionalProperties: false` на каждой ветке — «не требуется» значит
**запрещено**.

| `state` | `merge_sha` | `identity` | `type_hint` | `actor_class` |
|---|---|---|---|---|
| `merged` | resolved oid | обязательно | обязательно | обязательно |
| `not_merged` | `null` | запрещено | запрещено | запрещено |
| `not_found` | `null` | запрещено | запрещено | запрещено |
| `no_matching_pr` | `null` | запрещено | запрещено | запрещено |
| `actor_unavailable` | resolved oid | запрещено | запрещено | запрещено |

`merge_sha` — разрешённый merge-коммит связанного PR, а не эхо запроса: для
`no_matching_pr` он `null` именно потому, что запрошенный commit таким коммитом
не является.

### Матрица допустимости `state` × `request.kind`

Схема, а не дисциплина продюсера, обязана запрещать недостижимые комбинации:

| `state` | `request.kind: pr` | `request.kind: merge_sha` |
|---|---|---|
| `merged` | допустимо | допустимо |
| `not_merged` | **только здесь** | запрещено |
| `not_found` | допустимо | допустимо |
| `no_matching_pr` | запрещено | **только здесь** |
| `actor_unavailable` | допустимо | допустимо |

`not_merged` осмысленно только для PR-запроса (у SHA нет состояния «не слит»);
симметрично `no_matching_pr` осмысленно только для запроса по SHA.

**Известное ограничение эталонного продюсера.** Схема выше допускает `not_found`
для обоих `request.kind`, но текущий продюсер (`steward.approvalfacts.producer`)
на живом GitHub не может выпустить `not_found` для `request.kind: pr`: на
несуществующий номер PR `gh api graphql` возвращает `pullRequest: null`
**вместе** с top-level `errors: [{type: NOT_FOUND}]`, а §5.1 классифицирует
непустой `errors` как недоступность (`MechanicalFailure`, весь батч отменяется)
раньше, чем строка успевает стать записью `not_found`. Для `request.kind:
merge_sha` `not_found` достижим и наблюдался живьём: несуществующий oid
возвращает `{"data":{"repository":{"object":null}}}` без `errors`, exit `0`.
Открытый хвост — `approval-facts-not-found-vs-mechanical-failure` в `TODO.md`
steward'а (репозиторий-продюсер этого контракта); см. также
`docs/evidence/2026-08-21-approval-facts-v2-migration/manifest.md`, шаг 3.

## Инварианты валидного файла (читатель обязан проверить ВСЕ)

Нарушение любого делает файл `unreadable` целиком, а не «частично пригодным»:

1. первая и только первая строка — `header`;
2. `scope` непуст и не содержит дублей;
3. для каждого элемента `scope` существует ровно один `result`;
4. `result` вне `scope` запрещён;
5. дубли `result` запрещены;
6. `request` в `result` семантически равен ровно одному нормализованному
   элементу `scope` по типизированной идентичности `(kind, value)` — не
   побайтовому сравнению JSON-фрагментов строки. `merge_sha` остаётся
   наблюдаемым полем, не ключом;
7. поля соответствуют `state` (обе матрицы выше);
8. `generated_at` и `valid_until` соответствуют **единой канонической форме
   провода**, а не произвольному RFC 3339: UTC, суффикс `Z`, секундная
   точность — `YYYY-MM-DDTHH:MM:SSZ`. Это проверяется **схемой**
   (`SCHEMA.json` задаёт форму через `pattern`, не через `format`, — у
   `jsonschema` нет включённого по умолчанию чекера `date-time`, а
   опциональный `FormatChecker` не решает эту задачу без сторонней
   зависимости; полагаться на него значило бы сделать enforcement зависимым
   от того, подключил ли **потребитель** необязательный пакет), а не
   остаётся обязанностью читателя, как для многообразия форм RFC 3339 в
   общем случае. Продюсер пишет ровно эту форму; вендорируемому контракту
   одна каноническая форма провода полезнее произвольного RFC 3339;
9. алиасы одного мержа (`pr:42` и `merge_sha:<oid>` в одном scope) не
   противоречат друг другу: сравнивается кортеж
   `(state, merge_sha, identity, type_hint, actor_class)` — запись целиком за
   вычетом `request`. Отсутствующие по матрице полей значения — `null` с обеих
   сторон, не «несравнимые».

   **Известный пробел.** Сравнение работает только по записям с `merge_sha !=
   null`, то есть по `merged`/`actor_unavailable`. Запись с `merge_sha: null`
   (`not_found`, `no_matching_pr`, `not_merged`) в сравнение не входит вовсе —
   ей не с чем сойтись по ключу. Файл вида `pr:42 → merged, merge_sha=X`
   вместе с `merge_sha:X → not_found` (`merge_sha: null` по матрице полей)
   валиден по этому инварианту, хотя утверждает о SHA `X` две несовместимые
   вещи. Разрешение этого случая на стороне enforcement (не читателя) —
   **индекс разрешённых SHA проверяется раньше scope-по-идентичности
   запроса**, поэтому такой файл разрешается через индекс (`merged`), а не
   через отрицательный алиас; это решение читающего гейта, не форма файла,
   и здесь фиксируется только потому, что читатель этого контракта обязан
   знать: сам формат такую комбинацию не отвергает. Открытый хвост —
   `approval-facts-index-precedence-over-negative-alias` в `TODO.md`
   steward'а (репозиторий-продюсер этого контракта);
10. проверки времени, обязательные для **любого** читателя контракта, не только
    steward: `valid_until > generated_at`; оба — UTC; заявленная длительность
    `valid_until − generated_at` ≤ 30 суток; `generated_at` более чем на 300
    секунд в будущем — `unreadable`, а не «очень свежий файл». Значения — обе
    константы контракта, см. ниже;
11. **`header.repository` совпадает с наблюдаемым репозиторием читателя.**
    Единственный инвариант, требующий **внешнего ожидания** — инварианты 1–10
    проверяются по файлу самому по себе, этот сравнивает файл с тем, что читатель
    уже знает о своём окружении (нормализованный `owner/repo`, без учёта
    регистра, по полной паре, без суффиксного совпадения). Без этой проверки
    файл из другого репозитория с совпавшим merge SHA прошёл бы lookup —
    SHA-коллизия между форками/зеркалами не гипотетическая экзотика.

Усечённый JSONL — не валидный префикс: `header` обещает полный `scope`, и
недостающие записи читатель обязан обнаружить (инвариант 3).

## `scope_sha256` — корреляционная проверка, не доказательство

Не заменяет биекцию (инварианты 3–5): совпавший хеш не доказывает, что записи на
месте. Роль — поймать рассогласование заявки до сканирования и связать файл с
конкретным запросом.

Канонические байты: JSON-массив нормализованных объектов `request`,
отсортированный по `(kind, value)`, сериализация с фиксированными разделителями
`(",", ":")`, без пробелов, UTF-8, без escape non-ASCII (`ensure_ascii=False`,
`sort_keys=True`). Хеш — sha256 от этих байтов, с префиксом `sha256:`.

## Константы контракта

Одинаковы для любого потребителя — не политика steward, значения нормативно
фиксированы здесь и в `SCHEMA.json`:

- `schema_version = "2"`;
- допуск часов на будущее (инвариант 10) — **300 секунд**;
- верхняя граница заявленной длительности `valid_until − generated_at`
  (инвариант 10) — **2 592 000 секунд (30 суток)**.

Точное равенство заявленной длительности **текущему** значению
`approval_facts_lease_seconds` из `profiles/approval-policy.yaml` — проверка
гейта steward, не общий инвариант: у постороннего читателя нет доступа к чужой
политике, и требовать от него этого нельзя.

## Фикстуры (`fixtures/`)

Канон и для producer-тестов, и для вендоринга потребителем:

| Фикстура | Класс | Схема-валидна? |
|---|---|---|
| `clean.jsonl` | header + один `merged`-результат | ✅ |
| `negative_states.jsonl` | header со scope из четырёх запросов + четыре отрицательных/предельных результата (`not_merged`, `not_found`, `no_matching_pr`, `actor_unavailable`) | ✅ |
| `bad_state_for_kind.jsonl` | `state: not_merged` при `request.kind: merge_sha` — недостижимая по матрице комбинация | ❌ |
| `extra_field_on_negative.jsonl` | `state: not_found` с посторонним полем `identity` | ❌ |
| `bad_timestamp_format.jsonl` | `generated_at: "not-a-date"` — не канонической формы провода | ❌ |
| `missing_merge_sha_negative.jsonl` | `state: not_found` без поля `merge_sha` вовсе (матрица требует явный `null`, не отсутствие) | ❌ |

`clean.jsonl` и `negative_states.jsonl` несут **настоящий** `scope_sha256`,
пересчитанный по рецепту выше, а не правдоподобно выглядящее значение: формат
хеша схема проверяет, содержимое — нет, и фикстура с фиктивным дайджестом учила
бы доверять форме вместо содержимого.

## Версионирование

Ломающее изменение = новый каталог `v3/` рядом; `v2/` замораживается. Потребитель
с копией `v2` обязан классифицировать header `schema_version != "2"` как
unreadable/unsupported — никогда как pass.
