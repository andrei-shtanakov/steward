# eval/corpus/_ids.txt — append-only реестр id дефектов/non-defects (review-eval).
#
# Формат, одна запись на строку, last-wins по id:
#   "<id> <sha256 записи> <sha256 ядра идентичности>" — зарегистрирована;
#   "<id> ... reidentified"                           — смена идентичности,
#                                                       подтверждённая разметчиком;
#   "<id> deleted"                                    — надгробие: id израсходован;
#   "<id> <sha256 записи>"                            — старый формат: ядро
#                                                       идентичности неизвестно.
# Ядро идентичности — нормализованный file плюс scenario: оно отвечает «та же
# это запись», дайджест записи — «то же ли у неё содержимое». Правка вокруг
# ядра — перерегистрация; смена ядра — другой дефект (нужен новый id либо
# --reidentify).
# Надгробие терминально: строка с дайджестом после него делает реестр
# невалидным (повторное надгробие — нет, списание идемпотентно).
# id, однажды появившийся здесь, никогда не достаётся другой записи
# (steward.review_eval.corpus.check_registry сторожит это; он же требует, чтобы
# каждая закоммиченная версия продолжала каждого своего родителя, а рабочий
# файл — HEAD: историческую строку нельзя удалить ни правкой, ни коммитом, ни
# «удалить и вернуть»; сам файл — тоже, ни из рабочего дерева, ни коммитом). Правка живой
# записи законна и подтверждается новой строкой с новым дайджестом; id,
# ушедший из корпуса, списывается надгробием и не возвращается — ни под
# другим дефектом, ни под тем же содержимым: заводите новый id.
# Файл не редактируется руками: `review-eval corpus validate --register`
# дописывает недостающие строки, а надгробия — только с --retire-deleted
# (списание необратимо; на пустом каталоге кейсов оно запрещено вовсе).

# — YAML-ы в этой части сплита отсутствуют. Удалить строки нельзя (append-only
# проверяется по всей истории файла), а живой id без кейса — нарушение,
# поэтому здесь они **списаны** надгробиями. Черновики регистрирует часть 3 —
