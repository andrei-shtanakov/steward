# steward — spec governance layer (dogfood spec)

> Рабочее имя проекта: **steward** (провизорно). Управляет жизненным циклом спек, **не** исполняет.
> Это спека самого steward, написанная в его собственном формате (dogfood).
> Статус реализации: active bootstrap · Профиль: `team` (5 авторинговых артефактов) · Дата: 2026-07-18

## Что это

steward — тонкий слой поверх spec-runner/Maestro: проводит спеку через набор **аппрувнутых
артефактов** (гейтов), форсит порядок и трассируемость через git-PR/CODEOWNERS/CI, а на выходе
**компилирует вниз делегированием** (Decomposition→Maestro, Task Spec→spec-runner). Не пишет
`tasks.md`/`project.yaml` сам, не строит свою идентичность/RBAC.

Контекст и обоснование: [`spec/20-design.md`](spec/20-design.md) (раздел «Ключевые решения»).

## Реализовано сейчас

- `gate-check` — линтер governance-артефактов: completeness, traceability,
  status/git mirror, stale cascade, compile-block checks.
- `steward-compile` — compile-down emitters: Maestro `project.yaml` и
  delegation manifest для spec-runner leaf specs; golden tests держат контракт.
- `steward risk-classify` — risk-model classifier и waiver-модель.

`project.yaml` в корне — contract-check artifact, а не runtime config: он
должен оставаться byte-equal выводу `steward-compile project-yaml`.

авто-аппрувятся (анти-ceremony).

## Схема трассировки ID

```
REQ-xxx / NFR-xxx  (requirements)
      └─▶ DEC-xxx  (design decisions)  ──┐
      └─▶ AC-xxx   (acceptance criteria) ─┼─▶ WS-xxx (decomposition) ─▶ TASK-xxx (spec-runner)
```
Правило: каждый downstream-артефакт ссылается на upstream ID в `traces_to`. CI `gate-check`
проверяет, что висячих ссылок нет и upstream `APPROVED`.

## Файлы бандла

- `spec/00-charter.md` — проблема, scope, success-критерии
- `spec/10-requirements.md` — REQ + NFR
- `spec/20-design.md` — архитектура, решения, frontmatter-схема, профиль-YAML, gate-check контракт, CODEOWNERS
- `spec/30-acceptance.md` — acceptance-критерии + стратегия тестов
- `spec/40-decomposition.md` — workstreams → Maestro/spec-runner

## Аппрув-модель (git)

Артефакт = файл с frontmatter. Аппрув = PR, отревьюенный CODEOWNERS-ролью артефакта, → merge в
`main`. `status: approved` во frontmatter — **зеркало** git (git — primary). `gate-check` в CI
блокирует downstream, пока upstream не merged+approved, и метит stale при изменении upstream.

## Локальное ревью перед пушем (opt-in)

Быстрый фильтр, задающий те же вопросы, что чек `codex-review` в CI. Экономит
раунды CI: локальный прогон — секунды, раунд CI — минуты.

```bash
sh scripts/review/install-hook.sh     # поставить pre-push хук
sh scripts/review/local.sh            # разовый прогон без хука
sh scripts/review/local.sh --fetch    # то же, обновив базу с origin
```

Хук блокирует пуш на любом неположительном исходе. Отправить без ревью:
`git push --no-verify` — это штатное осознанное действие, а не нарушение.

Хук блокирует по построению, а не из-за поломки, ещё две обычные операции —
ревьюировать в них нечего, а «проверили одно, отправили другое» он не
допускает:

- **удаление ветки** — `git push origin --delete <ветка>`;
- **пуш тега**.

Штатный способ для обеих — `--no-verify`, например
`git push --no-verify origin --delete <ветка>`. В частности, чистка влитой
ветки после мержа из `CLAUDE.md` упрётся в эту блокировку сразу.

Хук зовёт `local.sh` без `--base` — значит диапазон всегда считается против
**ветки по умолчанию** (`origin/HEAD`), а не против цели будущего PR: узнать
цель заранее локально нечем, `@{upstream}` у только что запушенной ветки
указывает на неё же, и угадывание завело бы то же машинно-зависимое
поведение, против которого написан весь `§6`. Для ветки, ответвлённой не от
ветки по умолчанию (например от `release/1.0`), автоматический прогон из
хука сравнит не с тем — вердикт будет несопоставим с CI. Прогоните вручную
`sh scripts/review/local.sh --base <ветка-цель>` перед пушем такой ветки.

То же самое при пуше в **явно названный** чужой ref
(`git push origin hotfix:release/1.0`): хук по-прежнему сравнивает с веткой
по умолчанию, не с `release/1.0` — считать диапазон от имени принимающей
стороны означало бы для обычного `git push origin hotfix` (где имя
принимающей ссылки совпадает с именем ветки) ревьюить только новые коммиты
вместо полного PR-дифа, теряя сопоставимость с CI ровно там, где она нужна
чаще всего. Для пуша в именованный чужой ref тоже нужен ручной
`sh scripts/review/local.sh --base <ветка-цель>`.

**Локальный прогон не является гейтом и не производит governance evidence.** Он
идёт на машине разработчика, его ключом, и снимается флагом; проверить, что он
отработал, некому. Авторитет остаётся у чека `report` в CI. Локальный зелёный
не аргумент в PR.

Локально используются промпт, схема и скрипты из рабочего дерева — включая
незакоммиченные правки. В CI они читаются из `base`, чтобы автор патча не мог
переписать инструкции и порог своему же ревьюеру; локально такого разделения
нет по построению.

### Что видит ревьюер

По умолчанию — только диф. Если в репозитории есть
`.github/codex/review-context.txt`, ревьюеру дополнительно прикладывается
небольшой пакет перечисленных в нём файлов: по одному пути на строку,
комментарии через `#`, без glob'ов, только текст, потолки 64 КиБ на файл и
256 КиБ на пакет.

Смысл — в том, что ревьюер, не видящий соседний модуль, обязан поднимать
догадку о его поведении до `major` («а если продюсер вернёт 0 и молча ничего не
запишет»). Показав ему этот модуль, гипотезу превращают в проверяемое
утверждение. Пакет намеренно мал: полный доступ к репозиторию забрал бы у
ревьюера независимость — он читал бы код вместе с его допущениями.

**И список, и содержимое берутся из base-ревизии PR** (`git show <base>:<путь>`),
не из ветки. Автор PR не может ни подложить себе удобный файл, ни убрать
неудобный, ни переписать контекст под свой патч — его правки этих же файлов
ревьюер увидит только дифом, рядом с базовой версией.

Локально список и содержимое берутся так же — из merge-base, а не из рабочего
дерева. А вот сам `collect-context.sh` локально авторский, как и остальной кит
(см. абзац ниже): правя сборщик, вы увидите локально его правленую версию.
Авторитет остаётся у CI.

Отсутствие манифеста — штатное состояние: ревью идёт по одному дифу. А вот
манифест, который есть и не собирается (пропавший файл, превышенный потолок),
красит чек: ревью без контекста не должно выглядеть как ревью с ним.

Чего не хватило — ревьюер называет в `note`. Список пополняется правкой
`review-context.txt` в base, то есть обычным PR.
