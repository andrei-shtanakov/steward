# steward — spec governance layer (dogfood spec)

> Рабочее имя проекта: **steward** (провизорно). Управляет жизненным циклом спек, **не** исполняет.
> Это спека самого steward, написанная в его собственном формате (dogfood).
> Статус реализации: active bootstrap · Профиль: `team` (5 авторинговых артефактов) · Дата: 2026-07-18

## Что это

steward — тонкий слой поверх spec-runner/Maestro: проводит спеку через набор **аппрувнутых
артефактов** (гейтов), форсит порядок и трассируемость через git-PR/CODEOWNERS/CI, а на выходе
**компилирует вниз делегированием** (Decomposition→Maestro, Task Spec→spec-runner). Не пишет
`tasks.md`/`project.yaml` сам, не строит свою идентичность/RBAC.

Контекст и обоснование: [`spec/20-design.md`](spec/20-design.md) (раздел «Ключевые решения»).

## Реализовано сейчас

- `gate-check` — линтер governance-артефактов: completeness, traceability,
  status/git mirror, stale cascade, compile-block checks.
- `steward-compile` — compile-down emitters: Maestro `project.yaml` и
  delegation manifest для spec-runner leaf specs; golden tests держат контракт.
- `steward risk-classify` — risk-model classifier и waiver-модель.

`project.yaml` в корне — contract-check artifact, а не runtime config: он
должен оставаться byte-equal выводу `steward-compile project-yaml`.

авто-аппрувятся (анти-ceremony).

## Схема трассировки ID

```
REQ-xxx / NFR-xxx  (requirements)
      └─▶ DEC-xxx  (design decisions)  ──┐
      └─▶ AC-xxx   (acceptance criteria) ─┼─▶ WS-xxx (decomposition) ─▶ TASK-xxx (spec-runner)
```
Правило: каждый downstream-артефакт ссылается на upstream ID в `traces_to`. CI `gate-check`
проверяет, что висячих ссылок нет и upstream `APPROVED`.

## Файлы бандла

- `spec/00-charter.md` — проблема, scope, success-критерии
- `spec/10-requirements.md` — REQ + NFR
- `spec/20-design.md` — архитектура, решения, frontmatter-схема, профиль-YAML, gate-check контракт, CODEOWNERS
- `spec/30-acceptance.md` — acceptance-критерии + стратегия тестов
- `spec/40-decomposition.md` — workstreams → Maestro/spec-runner

## Аппрув-модель (git)

Артефакт = файл с frontmatter. Аппрув = PR, отревьюенный CODEOWNERS-ролью артефакта, → merge в
`main`. `status: approved` во frontmatter — **зеркало** git (git — primary). `gate-check` в CI
блокирует downstream, пока upstream не merged+approved, и метит stale при изменении upstream.

## Локальное ревью перед пушем (opt-in)

Быстрый фильтр, задающий те же вопросы, что чек `codex-review` в CI. Экономит
раунды CI: локальный прогон — секунды, раунд CI — минуты.

CI-ревью с 2026-08-28 — **opt-in фолбэк** (ревью по умолчанию — терминальный
прогон `devtools/review-pr.sh` от ai-prosto; SSOT —
`prograph-vault/authored/rules/git-workflow.md`): без лейбла `codex-review`
PR не ревьюируется CI вовсе (чек `report` красный с причиной «ревью
отложено» — это не находка). Полный прогон получает только PR с лейблом;
лейбл действует со следующего события (пуш или снятие драфта): само
навешивание прогон не запускает намеренно — иначе любой посторонний лейбл
пережигал бы прогон на неизменном SHA.

```bash
sh scripts/review/install-hook.sh     # поставить pre-push хук
sh scripts/review/local.sh            # разовый прогон без хука
sh scripts/review/local.sh --fetch    # то же, обновив базу с origin
```

**Хук наследует окружение процесса `git push`.** Задайте `REVIEW_HARNESS` в
профиле shell — и `git push` из терминала пойдёт на claude. GUI/IDE-клиенты
git, не читающие профиль shell, переменной не увидят, и хук честно уйдёт на
умолчание `codex`; проверяйте из того же окружения:
`sh scripts/review/local.sh --print-review-cmd`. Экспорт `REVIEW_HARNESS=claude`
в профиле shell **валит `git push`** (код 2, хук блокирует) в любом
репозитории, чей вендоренный кит ещё не содержит адаптер `harness-claude`, —
это fail-closed поведение по конструкции («кит обновлён наполовину», ниже),
а не баг; либо ре-вендорьте такие копии кита, либо задавайте переменную
per-репо/per-сессию, а не глобально в профиле.

Хук блокирует пуш на любом неположительном исходе. Отправить без ревью:
`git push --no-verify` — это штатное осознанное действие, а не нарушение.

Хук блокирует по построению, а не из-за поломки, ещё две обычные операции —
ревьюировать в них нечего, а «проверили одно, отправили другое» он не
допускает:

- **удаление ветки** — `git push origin --delete <ветка>`;
- **пуш тега**.

Штатный способ для обеих — `--no-verify`, например
`git push --no-verify origin --delete <ветка>`. В частности, чистка влитой
ветки после мержа из `CLAUDE.md` упрётся в эту блокировку сразу.

Хук зовёт `local.sh` без `--base` — значит диапазон всегда считается против
**ветки по умолчанию** (`origin/HEAD`), а не против цели будущего PR: узнать
цель заранее локально нечем, `@{upstream}` у только что запушенной ветки
указывает на неё же, и угадывание завело бы то же машинно-зависимое
поведение, против которого написан весь `§6`. Для ветки, ответвлённой не от
ветки по умолчанию (например от `release/1.0`), автоматический прогон из
хука сравнит не с тем — вердикт будет несопоставим с CI. Прогоните вручную
`sh scripts/review/local.sh --base <ветка-цель>` перед пушем такой ветки.

То же самое при пуше в **явно названный** чужой ref
(`git push origin hotfix:release/1.0`): хук по-прежнему сравнивает с веткой
по умолчанию, не с `release/1.0` — считать диапазон от имени принимающей
стороны означало бы для обычного `git push origin hotfix` (где имя
принимающей ссылки совпадает с именем ветки) ревьюить только новые коммиты
вместо полного PR-дифа, теряя сопоставимость с CI ровно там, где она нужна
чаще всего. Для пуша в именованный чужой ref тоже нужен ручной
`sh scripts/review/local.sh --base <ветка-цель>`.

**Локальный прогон не является гейтом и не производит governance evidence.** Он
идёт на машине разработчика, его ключом, и снимается флагом; проверить, что он
отработал, некому. Авторитет остаётся у чека `report` в CI. Локальный зелёный
не аргумент в PR.

Локально используются промпт, схема и скрипты из рабочего дерева — включая
незакоммиченные правки. В CI они читаются из `base`, чтобы автор патча не мог
переписать инструкции и порог своему же ревьюеру; локально такого разделения
нет по построению.

### Харнесс ревьюера

Кит читает переменные `REVIEW_*` только из **окружения процесса** (ни файла,
ни git-конфига):

| Переменная | Значения | Умолчание |
|---|---|---|
| `REVIEW_HARNESS` | `codex` \| `claude` | `codex` |
| `REVIEW_MODEL` | имя модели харнесса | codex — без `-m`; claude — `claude-opus-5` |
| `REVIEW_EFFORT` | уровень reasoning | не задан — флаг не добавляется |
| `REVIEW_CMD` | команда целиком (с флагами) | не задана |

Непустой `REVIEW_CMD` побеждает всё остальное; пустой — как незаданный.
`REVIEW_HARNESS=""`, `REVIEW_MODEL=""` и `REVIEW_EFFORT=""` — ошибка
конфигурации (код 2), а не умолчание: пустое значение приходит только от
сломанной настройки, и молча уйти на умолчание значило бы сжечь тот лимит,
ради которого переменная выставлялась. Непустые `REVIEW_MODEL` и
`REVIEW_EFFORT` обязаны быть ОДНИМ словом из алфавита `A-Za-z0-9._:/@+-` (код
2 иначе) — обе они собираются в команду ревьюера текстом, и тот же текст
затем расщепляется на слова, так что значение с пробелом или флагом внутри
подставило бы ревьюеру лишний argv. Значение уходит харнессу как есть
(`codex exec -c model_reasoning_effort=<уровень>` или `harness-claude
--effort <уровень>`) и входит в отпечаток команды наравне с моделью. Что
именно будет запущено, печатает `sh scripts/review/local.sh --print-review-cmd`.

Sidecar-артефакты для eval (спека review-eval §7): `REVIEW_VERDICT_OUT`
(`local.sh`) сохраняет вердикт ревью атомарно, ещё до применения порога —
доступен и когда прогон падает кодом 1; `REVIEW_USAGE_OUT` (адаптер
`harness-claude`) пишет нормализованный usage/стоимость, в том числе при
ошибке ревьюера. Оба пути задаются окружением, оба не входят в отпечаток,
пустое значение любого из них — ошибка конфигурации (код 2).

Для claude нужен `claude` CLI и `jq` в `PATH`; адаптер
`scripts/review/harness-claude` — обязательный член кита (переходным он был
только в релизе `a2d7e71` до волны ре-вендора devtools#228), и
`REVIEW_HARNESS=claude` при его отсутствии — именованный отказ «кит обновлён
наполовину», а не `command not found`. Строка команды попадает в отпечаток
ревью: умолчание `codex exec` не изменилось, старые наследования вердиктов
остаются валидными; переключение харнесса или модели — другой ревьюер,
наследовать нельзя.

### Что видит ревьюер

Диф и рабочее дерево репозитория в **base-ревизии** (read-only): ревьюер обязан
проверять чтением то, что лежит в репо, а догадки о внешних фактах остаются
ограничены `minor`. Чекаут в CI — база, поэтому автор PR не может подсунуть
ревьюеру свои версии файлов: его правки видны только дифом. Если в репозитории есть
`.github/codex/review-context.txt`, ревьюеру дополнительно прикладывается
небольшой пакет перечисленных в нём файлов: по одному пути на строку,
комментарии через `#`, без glob'ов, только текст, потолки 64 КиБ на файл и
256 КиБ на пакет.

Пакет — курируемые указатели «начни отсюда», не граница: всё остальное ревьюер
может открыть сам. Смысл пакета — сразу положить перед ревьюером модули, от
которых зависит корректность патча, не тратя его шаги на поиск.

**И список, и содержимое берутся из base-ревизии PR** (`git show <base>:<путь>`),
не из ветки. Автор PR не может ни подложить себе удобный файл, ни убрать
неудобный, ни переписать контекст под свой патч — его правки этих же файлов
ревьюер увидит только дифом, рядом с базовой версией.

Локально список и содержимое берутся так же — из merge-base, а не из рабочего
дерева. А вот сам `collect-context.sh` локально авторский, как и остальной кит
(см. абзац ниже): правя сборщик, вы увидите локально его правленую версию.
Авторитет остаётся у CI.

Путь манифеста (и пути внутри него) — пути **в дереве base от корня
репозитория**, не пути в файловой системе: `local.sh` из подкаталога собирает
тот же пакет, что и из корня, а абсолютный путь или `..` в
`REVIEW_CONTEXT_MANIFEST` сборщик отвергает кодом 2.

Отсутствие манифеста — штатное состояние: ревью идёт по одному дифу. А вот
манифест, который есть и не собирается (пропавший файл, превышенный потолок),
красит чек: ревью без контекста не должно выглядеть как ревью с ним.

Чего не хватило — ревьюер называет в `note`. Список пополняется правкой
`review-context.txt` в base, то есть обычным PR.

### Область ревью: прозаические пути не доходят до модели

Кит по умолчанию НЕ отправляет ревьюеру прозаические пути диапазона —
`*.md`, `*.txt`, `TODO.md`, `docs/*`, `workstreams/*/spec/*` — по правилу
`scripts/review/prose-paths.env` (пиненая вендор-копия SSOT
`devtools/contracts/review-scope/v1/prose-paths.env`, формат: `PROSE=`/
`CODE_OVERRIDE=` — глобы через пробел, `CODE_OVERRIDE` сильнее `PROSE` и
держит кодом при любом расширении пути вроде `.github/*`, `contracts/*`,
`fixtures/*`, `schemas/*`, `*requirements*.txt`, `*constraints*.txt`). Забор
ставится ПО ПРОЗЕ: код — всё, что в `PROSE` не перечислено, — обратная
формулировка вывела бы из-под ревью классы файлов вроде
`.github/workflows/*.yml`, где уже был живой дефект.

Три разных исхода диапазона:

| Диапазон | Код выхода | Смысл |
| --- | --- | --- |
| пуст сам диапазон (`base == head`) | `0` | ревьюер не вызывался, наследовать нечего |
| смешанный или чисто кодовый | `0`/`1`/`3` (как обычно) | ревьюеру уходит только кодовая часть; кодовый диапазон не меняется вовсе — отпечаток совпадает с прогоном без фильтра |
| диапазон непуст, но ПОСЛЕ фильтра не осталось ничего (весь диф — проза) | `5` | «ревьюировать нечего» — НЕ то же самое, что код `0`: потребитель обязан различать эти два кода, иначе опубликует approve, которого ревьюер не выносил. Хук `pre-push` код 5 трактует как успешный пропуск пуша |

Правило — fail-open в сторону ревью, не в сторону молчания: нет файла
правила, файл нечитаем, ключ `PROSE` не назван, ключ определён больше
одного раза, пустое значение, отсутствует обязательный `CODE_OVERRIDE` —
**любая** из этих причин отключает фильтр целиком, ревьюер получает полный
диф. Недоказанная проза не прячется; негодное правило означает «ревью как
без фильтра», а не «ревью пропущено».

Разово отключить фильтр (например для ревью самого правила путей) —
`sh scripts/review/local.sh --include-prose` или `REVIEW_INCLUDE_PROSE=1`;
флаг сильнее переменной только в сторону включения, оба выключить фильтр
обратно не могут. Любое другое значение переменной (включая `0`) —
config-отказ кодом 2, а не тихое «выключено»: явная, но сломанная настройка
не читается молча как её противоположность.

### Возврат прозы под ревью: `review-scope.env`

Потребитель кита может **вернуть себе** часть или всю уже отфильтрованную
фильтром выше прозу — без `--include-prose`/`REVIEW_INCLUDE_PROSE` (оба
разовые, локальные, требуют ручного флага при каждом прогоне) — постоянно,
через `.github/codex/review-scope.env` в своём репозитории:

| `PROSE_REVIEW=` | Эффект |
| --- | --- |
| файла нет | `off` — фильтр работает как обычно (умолчание) |
| `off` | то же самое явно |
| `paths` | возвращает под ревью только пути из `PROSE_REVIEW_PATHS` (глобы через пробел, обязателен при `paths`) |
| `all` | отключает фильтр целиком — ревьюер видит весь диф, как `--include-prose` |
| что угодно ещё | отказ кодом 2: неразобранный конфиг нельзя молча читать в пользу МЕНЬШЕГО ревью |

**Конфиг умеет только вернуть файлы ревьюеру — спрятать НОВОЕ, за пределами
уже пиненого `prose-paths.env`, им нельзя.** Расширение skip-набора (что
именно считается прозой) остаётся исключительно в самом `prose-paths.env`,
правка которого проходит вендорингом, не локальным конфигом репо. Иначе
любой потребитель кита мог бы односторонне спрятать от своего же ревьюера
произвольный путь — ровно то, против чего написан весь фильтр области.

Конфиг читается **из base** (`git show "$mb:.github/codex/review-scope.env"`),
не из рабочего дерева PR: иначе патч мог бы отключить собственное ревью,
добавив себе `PROSE_REVIEW=all` в том же PR.

### Насколько ревьюер хорош — измерение

`review-eval` прогоняет настоящий кит по прошлым PR с известным ответом и
печатает метрики с явными знаменателями: precision блокирующих находок,
recall по `major`/`blocker`, доля ложных блокировок, доля находок с
разрешимым evidence, стоимость и длительность. Корпус кейсов живёт в
`eval/corpus/` (ground truth — размеченный дефект с устойчивым id), прогоны —
в git-игнорируемом `eval/runs/`. Каждый кейс измеряется в detached worktree на
историческом `head_sha`, объект измерения — текущий кит steward, и прогон
никогда не касается сети. Как размечать кейс, читать отчёт, вести очередь
adjudication и сравнивать варианты модели — `docs/review-eval.md`.
