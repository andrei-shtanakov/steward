# Requirements — governance-панель бандла (WS-005)

## Функциональные требования

#### FR-01: Read-only состояние бандла
Панель показывает по бандлу: артефакт → статус → блокер. Только чтение. → G-01
**Priority**: 🔴 Must
**Acceptance**: для бандла с ≥1 finding оператор видит артефакт и текст блокера
с одного экрана, не открывая файлов.

#### FR-02: Единственный источник — versioned `gate_verdicts.jsonl`
Данные панели приходят только из файла вердиктов, эмитированного steward
gate-check. Dispatcher не вычисляет вердикты сам и не запускает steward. → G-02
**Priority**: 🔴 Must
**Acceptance**: collector не импортирует steward и не исполняет его CLI; при
отсутствии файла панель показывает no-data, а не результат собственных вычислений.

#### FR-03: Нечитаемое ≠ чистое
Битый JSON, неизвестная `schema_version`, ошибка ввода-вывода → различимое
состояние unreadable. Ни один класс нечитаемости не отображается как pass. → G-02
**Priority**: 🔴 Must
**Acceptance**: golden-фикстура каждого класса повреждения рендерится в не-pass
состояние с указанием причины.

#### FR-04: Устаревшее ≠ чистое
Вердикт, чьё происхождение (source commit / чистота дерева) не совпадает с
текущим состоянием `spec/` бандла, отображается как stale, не pass. → G-02
**Priority**: 🔴 Must
**Acceptance**: фикстура с расхождением source commit → состояние stale.

#### FR-05: Свежесть и происхождение видимы
Оператор видит, когда и из какого состояния репо сгенерирован вердикт. → G-02
**Priority**: 🟠 Should
**Acceptance**: timestamp генерации и source commit отображаются рядом со
статусом бандла.

## Нефункциональные требования

#### NFR-01: Чтение работает от диска
**Priority**: 🔴 Must
**Category**: availability
**Target**: бандл рендерится при остановленных процессах всех наблюдаемых репо;
сеть на пути чтения не используется. → CON-01

#### NFR-02: Fail-closed чтение
**Priority**: 🔴 Must
**Category**: safety
**Target**: property-тест по классам ошибок чтения/парсинга: ноль путей,
ведущих из ошибки в состояние pass. → G-02

## Ограничения

- **CON-01** Dispatcher читает артефакты наблюдаемых репо с диска; наблюдаемые
  проекты не обязаны быть запущены (действующий принцип dispatcher).
- **CON-02** Канон схемы вердиктов живёт в steward; потребители вендорят
  пиненую копию (правило repo-boundaries); две гарантии — copy-integrity и
  upstream-drift — раздельны.
- **CON-03** Shipped-код не резолвит пути соседних репо напрямую — только
  сконфигурированные корни наблюдаемых репо.

## Success-метрики

- **M-01** В golden-сьюте 0 фикстур классов повреждено/устарело/нерезолвимо,
  отрендеренных как pass. → G-02
- **M-02** Оператор определяет блокер бандла с одного экрана без открытия
  файлов — подтверждено dogfood-прогоном на бандле самого steward. → G-01

## Вне scope

- **OUT-01** Write-действия из панели (approve, merge, re-run gate).
- **OUT-02** История и тренды вердиктов во времени.
- **OUT-03** Мультипользовательская авторизация.
