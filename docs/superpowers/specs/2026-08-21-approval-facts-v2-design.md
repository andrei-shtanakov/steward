# `approval-facts/v2` — внешний контракт merge-акторов и миграция release-гейта

> Дизайн утверждён владельцем 2026-08-21. Запрос — steward#72 (inbox,
> from `dispatcher#agent-merge-observability`). Реализация — по плану, который
> пишется из этой спеки.

## 1. Зачем

`dispatcher#agent-merge-observability` заблокирован: у него нет источника, из которого
видно, кто смержил PR. Оба обходных пути отвергнуты на ревью дизайна и повторять их
запрещено — читать `profiles/approval-policy.yaml` из чекаута steward значит нарушить
границы полирепо (контракт потребляется пиненой копией внутрь, а не импортом из пути
соседа), а воспроизвести `classify_actor` у себя значит завести **два policy engine**,
способных разойтись.

Владелец классификации — steward. Наружу должен выйти переносимый evidence-контракт:
raw facts плюс итоговая классификация плюс provenance применённой политики.

Сегодня `approval-facts` существует только как Python (`src/steward/approvalfacts.py`),
в `contracts/` его нет, вендорить нечего. Задача — **graduation** внутреннего формата в
контракт, а не расширение payload.

Без этого контракта действует ADR-ECO-008 D6: нет наблюдаемости — прогон обязан вести
себя как `merge_authority: human`.

## 2. Границы работы

**Входит:** контракт `contracts/approval-facts/v2/`, переписанный продюсер, эмиссия в
`.steward/`, миграция `check_approval_evidence` на v2, регрессионный набор, migration
acceptance на реальных мержах.

Продюсер, внешний контракт и внутренний гейт — **одна атомарная миграция**. Разнести их
значило бы сознательно оставить две семантики approval-facts, одна из которых не имеет
ни scope, ни completeness, ни lease.

**Не входит:** панель dispatcher и его read-модель (их стадия 2, после вендоринга);
аномалия declared-vs-observed (нужен `merge_authority`, которого сегодня нет нигде);
fsync-долг `verdicts/emitter.py` (отдельный TODO, см. §10).

## 3. Почему v2, а не v1

Текущий формат уже маркирует себя `approval-facts/v1` (`src/steward/approvalfacts.py`,
докстринг модуля), его принимает release-гейт и он зафиксирован live evidence прогона
2026-08-09. Публиковать под тем же именем несовместимую форму значит задним числом
переписать то, что уже доказано.

- новый внешний контракт — `contracts/approval-facts/v2/`;
- CLI после миграции пишет **только** v2;
- гейт читает **только** v2;
- v1 получает документированный статус legacy/internal и **явную ошибку**
  «unsupported legacy approval-facts/v1» — не молчаливую интерпретацию;
- рантайм не поддерживает два формата параллельно.

## 4. Файл

`<repo-root>/.steward/approval_facts.jsonl` — рядом с `gate_verdicts.jsonl`, тот же
бандл, gitignored локальный артефакт.

JSONL выбран не ради симметрии с `gate-verdicts/v1`, а потому что даёт естественную
одну запись на запрошенный элемент, не требует искусственного SHA-ключа для
отрицательных результатов и позволяет изолировать в фикстурах malformed / duplicate /
missing / extra result. Симметрия — приятное следствие: у потребителя уже есть
проверенная дисциплина чтения (`dispatcher/core/governance.py`).

### 4.1 Header

Первая и **только первая** строка.

```json
{"kind":"header","schema_version":"2","repository":"owner/repo",
 "generated_at":"2026-08-21T09:00:00Z","valid_until":"2026-08-22T09:00:00Z",
 "policy_version":1,"policy_digest":"sha256:…","complete":true,
 "scope_sha256":"sha256:…",
 "scope":[{"kind":"pr","value":42},{"kind":"merge_sha","value":"abc…"}]}
```

`complete: true` — заявление продюсера, а не доказательство. Читатель **обязан**
проверить его сам (§4.3).

### 4.2 Result

По одной записи на каждый элемент scope.

```json
{"kind":"result","request":{"kind":"pr","value":42},"state":"not_merged","merge_sha":null}
{"kind":"result","request":{"kind":"merge_sha","value":"abc…"},"state":"merged",
 "merge_sha":"abc…","identity":"github:merge-broker","type_hint":"Bot",
 "actor_class":"agent"}
```

**Пять терминальных состояний наблюдения:**

| state | значение |
|---|---|
| `merged` | merge-событие существует, актор получен |
| `not_merged` | PR существует, `mergeCommit == null` |
| `not_found` | PR/commit доказанно отсутствует в доступном репозитории |
| `no_matching_pr` | commit существует, но не является merge-коммитом связанного PR |
| `actor_unavailable` | merge существует, но `mergedBy` отсутствует или неразрешим |

**Классификация — отдельное поле, а не состояние.** Для `state: merged` с доступным
актором обязательно `actor_class: human | agent | unknown`. «Классифицировано как
unknown» выражается как `state: merged` + `actor_class: unknown`, а **не** шестым
состоянием: иначе `human`/`agent` представлены полем, а `unknown` внезапно типом
результата, и схема становится асимметричной.

**Матрица полей.** `SCHEMA.json` нормативен; таблица — его читаемая форма.
`additionalProperties: false` на каждой ветке, поэтому «не требуется» означает
**запрещено**, а не «необязательно».

| state | `merge_sha` | `identity` | `type_hint` | `actor_class` |
|---|---|---|---|---|
| `merged` | resolved oid | обязательно | обязательно | обязательно |
| `not_merged` | `null` | запрещено | запрещено | запрещено |
| `not_found` | `null` | запрещено | запрещено | запрещено |
| `no_matching_pr` | `null` | запрещено | запрещено | запрещено |
| `actor_unavailable` | resolved oid | запрещено | запрещено | запрещено |

`merge_sha` — **разрешённый** merge-коммит связанного PR, а не эхо запроса. Для
`no_matching_pr` он `null` именно потому, что запрошенный commit таким коммитом не
является: эхо запроса здесь создало бы видимость разрешения.

`state: merged` по определению влечёт разрешённого актора: случай «мерж есть, актора
нет» — это `actor_unavailable`, отдельное состояние.

### 4.3 Инварианты валидного файла

Читатель обязан проверить **все**; нарушение любого делает файл `unreadable` целиком,
а не «частично пригодным»:

1. первая и только первая строка — `header`;
2. `scope` непуст и не содержит дублей;
3. для каждого элемента `scope` существует ровно один `result`;
4. `result` вне `scope` запрещён;
5. дубли `result` запрещены;
6. `request` в `result` побайтово совпадает с исходным идентификатором из `scope`;
   `merge_sha` остаётся **наблюдаемым полем**, а не ключом;
7. поля соответствуют `state`;
8. `generated_at` и `valid_until` — timezone-aware RFC 3339 UTC.

Так усечённый JSONL перестаёт быть валидным префиксом: header обещает полный scope, и
читатель обнаруживает недостающие записи.

### 4.4 `scope_sha256` — корреляционная проверка, не доказательство

`scope_sha256` **не заменяет** биекцию (инварианты 3–5): совпавший хеш не доказывает,
что записи на месте. Его роль — поймать рассогласование заявки до сканирования и
связать файл с конкретным запросом.

Канонические байты определяются нормативно: JSON-массив нормализованных объектов
`request`, отсортированный по `(kind, value)`, сериализация с фиксированными
разделителями `(",", ":")`, без пробелов, UTF-8, без escape non-ASCII. Хеш — sha256 от
этих байтов.

## 5. Продюсер

### 5.1 Механический сбой ⇒ файла нет

Публикация не происходит вовсе при: транспортной ошибке, ошибке авторизации,
**непустом `errors`** в ответе GraphQL, malformed payload, неисчерпанном обходе,
ошибке записи.

Батч публикуется, только если терминальная запись получена **для каждого** элемента
объявленного scope. Файл означает «весь объявленный scope опрошен до определённого
результата», а не «все элементы оказались merged».

### 5.2 Три дефекта текущего продюсера — в обязательном scope работы

1. **`repository or {}`** (`_resolve_by_merge_sha`, `_resolve_by_pr`) схлопывает
   `repository: null` в пустой словарь и поднимает «not found». `repository: null`
   может означать auth/visibility failure и **не может** читаться как отсутствие:
   это механический сбой. Допустимый `not_found` — только когда `repository != null`,
   ошибок нет, а `pullRequest == null`.
2. **`_run_graphql` не смотрит в `errors`** — проверяется лишь код возврата `gh`.
   Любой непустой `errors` — недоступность результата.
3. **Ключ результата — merge SHA.** У неслитого PR SHA нет вовсе, поэтому текущая
   структура физически не может выразить `not_merged`. Результат ключуется **исходным
   запросом**; разрешённый SHA — поле.

### 5.3 Исчерпывающий обход

`associatedPullRequests(first:10)` сегодня идёт **без `pageInfo`**: усечение даже не
детектируется, и при одиннадцати связанных PR продюсер молча ответил бы «совпадения
нет». Под этим контрактом это дало бы **ложный `no_matching_pr`**.

Запрос обязан нести `pageInfo { hasNextPage endCursor }` и обходить страницы до конца.
Потолка нет: любой потолок воспроизводит ту же ложь. Если санитарный предел всё же
нужен, его превышение — механический сбой, а не отрицательный факт.

## 6. Транзакция и свежесть

### 6.1 Delete-before-attempt

1. снять прежнюю публикацию;
2. fsync каталога;
3. выполнить полную материализацию;
4. при успехе опубликовать атомарно: temp в том же каталоге → flush + fsync →
   `os.replace` → fsync каталога;
5. при любом сбое источник остаётся отсутствующим.

Обоснование: отсутствие источника здесь — определённое и **безопасное** состояние
(D6 переводит прогон в `merge_authority: human`). Устаревшее, выглядящее актуальным, —
состояние **опасное**. Удаление перед попыткой превращает опасное в безопасное.

Транзиентный сбой ухудшает доступность, но не создаёт ложного контроля.

### 6.2 Чего delete-before-attempt не решает

Старый файл сохранится, если новая попытка **вообще не стартовала**: планировщик не
сработал, машина выключена, workflow отключён. Поэтому delete-before-attempt нельзя
описывать как полное доказательство свежести. Закрывают это два свойства контракта.

### 6.3 Scope-ограниченность

Actor facts исторического мержа неизменяемы и действуют **только внутри объявленного
scope**. Читатель никогда не трактует файл как «все актуальные мержи»:

- запрошенный PR/SHA есть в scope и имеет result → наблюдение применимо;
- запрошенный PR/SHA отсутствует в scope → `unknown` **независимо от возраста файла**.

Это само по себе исключает применение старого файла к новому мержу.

### 6.4 Lease

Классификация зависит от изменяемой политики, поэтому header несёт `policy_version`,
`policy_digest` и **нормативный срок действия** `valid_until` — lease продюсера, а не
эвристика читателя по возрасту.

После `valid_until`: raw forge facts остаются исторически истинными, но `actor_class` и
файл как operational observation становятся stale; D6 переводит authority в `human`.

Второй marker-файл в v2 не заводится: он дал бы более подробную диагностику попытки, но
missed-run без lease всё равно не решает.

## 7. Конфигурация lease

Ключ в `profiles/approval-policy.yaml` — политика уже аудируема и уже входит в digest,
поэтому изменение lease честно видно как изменение политики.

```yaml
approval_facts_lease_seconds: 86400
```

Требования загрузчика:

- обязательный **положительный int**; `bool` запрещён (как и для `agent_merge_allowed`:
  truthy-скаляр — `PolicyError`, не приведение);
- верхняя граница — **2 592 000 секунд (30 суток)**, зашита в загрузчик; превышение —
  `PolicyError`, не усечение. Граница нужна, чтобы опечатка в порядке величины
  (`864000000` вместо `86400`) не выдала многолетнюю lease, читаемую как свежесть;
- `valid_until == generated_at + approval_facts_lease_seconds`, оба timezone-aware
  RFC 3339 UTC;
- случайное число в схему не зашивается: `SCHEMA.json` требует timestamp, длительность
  приходит из конфига.

`policy_version` в header — значение ключа `version` из того же файла политики
(сегодня `1`); это заявленная версия семантики, а `policy_digest` — доказательство
конкретных байтов. Одно не заменяет другое: версия может не измениться при правке
списков личностей.

`policy_digest` — sha256 по **сырым байтам** `profiles/approval-policy.yaml`. Комментарий
является частью аудируемого артефакта политики, поэтому его изменение честно
инвалидирует evidence.

## 8. Миграция гейта

### 8.1 Гейт остаётся комбинатором

Файл владеет **per-item наблюдением**; гейт комбинирует пять осей:

```
git provenance
  × доступность и свежесть контракта
  × членство в scope
  × терминальный результат
  × действующая политика
```

`agent_merge_allowed` остаётся решением **гейта** по текущей политике. Продюсер не
превращает `actor_class: agent` в вердикт одобрения.

### 8.2 Где какое состояние живёт

Часть состояний существует именно **вне** result:

| наблюдение | источник |
|---|---|
| файла нет | отсутствие артефакта |
| файл malformed / incomplete | нарушение инвариантов §4.3 |
| lease истёк | `valid_until` в header |
| `policy_digest` ≠ текущим байтам политики | сравнение в гейте |
| мерж вне объявленного scope | `unknown` для этого мержа |
| `state: actor_unavailable` | result |
| `state: merged` + `actor_class: unknown` | result |
| `state: merged` + `actor_class: human`/`agent` | result → policy path |

**Гейт сравнивает `policy_digest` с текущими сырыми байтами политики и fail-closed при
несовпадении, даже если lease ещё действует.** Наблюдение, классифицированное по другой
политике, не является наблюдением по текущей.

### 8.3 Пути ввода

Один формат, два явно выбранных пути:

- `steward approval-facts` по умолчанию пишет `.steward/approval_facts.jsonl`;
  `--out <path>` — явный override для тестов, offline-материализации и приёмки;
- `gate-check` по умолчанию читает путь бандла; `--approval-facts <path>` — явный
  override, принимающий **только v2**.

Без согласования ad-hoc `--out` порождал бы файл, который собственный гейт steward не
умеет использовать.

## 9. Приёмка

### 9.1 Регрессия (обязательный набор)

1. provenance absent;
2. evidence file absent;
3. malformed / incomplete / stale;
4. мерж вне scope;
5. actor unavailable;
6. classified unknown;
7. human;
8. agent denied;
9. agent allowed;
10. стадия `authoring` не запускает approval-гейт вовсе;
11. артефакт вне default branch остаётся вне охвата.

### 9.2 Migration acceptance на реальных мержах

На мержах live-прогона 2026-08-20: `e04b0c9` (человек, `github:andrei-shtanakov`,
`User`) и `2214579` / `05aa16e` (`github:merge-broker`, `Bot`). Результаты обязаны
остаться **эквивалентными по enforcement**, но пройти через scope, lease и терминальные
состояния v2.
