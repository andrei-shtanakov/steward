# codex-review kit — дорожная карта качества (план владельца, 2026-08-23)

Источник: решение владельца после замера на steward#96/#97. Контекст замера:
шесть «зрячих» раундов ревью (после доступа к репозиторию) дали 19/20
подтверждённых находок и 0 ложных, но цикл «чинить до пустого вердикта» не
сходится и стоит ~$0.5 за раунд. Дальше качество повышают изменения ниже, в
порядке приоритета владельца. Чекбоксы — в `TODO.md` §10a; этот файл — полная
формулировка, чтобы пункты не усыхали при пересказе.

## P0 — устранить потенциальный ложный зелёный

`review-kit-ci-migration`: CI на общих скриптах кита (`build-prompt.sh` в
`review`, только `apply-threshold.sh` в `report`, без дублирующего разбора
JSON/severity в YAML, обязательная base-проверка присутствия доверенных
файлов). **Сверено 2026-08-23: уже выполнено арками #92/#93**, чекбокс снят.

## P1 — дать Codex итоговое дерево PR (`review-kit-final-tree`)

Главное улучшение качества. Сейчас модель получает дерево base, текст дифа и
статический пакет из base — и обязана мысленно восстанавливать новое состояние
файлов; на больших патчах это источник ложных находок.

Целевая сборка рабочего дерева:

1. Из base скопировать в доверенный временный каталог: review prompt, JSON
   schema, `build-prompt.sh`, `apply-threshold.sh` (и `collect-context.sh`).
2. После этого checkout сделать на merge commit PR или head SHA.
3. Ничего из PR не исполнять: никаких pytest, shell-скриптов, package hooks и
   импортов Python.
4. Запустить Codex с read-only доступом к получившемуся дереву.
5. Диф передавать как указатель на область ревью, а не как единственное
   представление изменений.

Формула: **инструкции и порог — base; код для чтения — итоговое дерево PR; код
для исполнения — никакой.** Доверенная управляющая плоскость сохраняется, а
модель читает настоящие версии изменённых файлов и ходит по импортам.

## P1 — переписать шкалу severity (`review-kit-severity-rewrite`)

Текущее «blocker — код неверен…» раздуто: практически любой баг — «код
неверен», граница blocker/major не определена. Новая шкала:

- **blocker** — эксплуатация уязвимости, необратимая потеря/повреждение данных,
  обход authority boundary либо гарантированная невозможность основного
  сценария; мерж недопустим;
- **major** — воспроизводимый функциональный дефект, нарушение публичного
  контракта, fail-open или значимая регрессия;
- **minor** — локальный дефект с ограниченными последствиями, но с конкретным
  сценарием;
- **nit** — только стиль; лучше вообще не возвращать.

Для blocker и major обязательны: файл и строка; конкретный вход или
последовательность событий; наблюдаемый неправильный результат; ссылка на
проверенный код, подтверждающий предпосылку; краткое объяснение, почему
существующие проверки это не ловят. Нет одного пункта — находка не блокирует.

## P1 — сократить промпт (`review-kit-prompt-diet`)

Текущий `review-prompt.md` длинный и несёт историю прошлых ошибок, устройство
маркеров и слои предостережений — reasoning budget уходит на интерпретацию
процесса. Оставить четыре раздела: (1) что ревьюируется; (2) какие инструменты
и файлы доступны; (3) условия валидной находки; (4) шкала severity и формат
ответа. Механику доверия к base и маркеры обеспечивает runner, а не проза.
Целевой объём ~700–1200 слов.

## P1 — статический контекст не основной механизм (`review-kit-context-demotion`)

`.github/codex/review-context.txt` заточен под approvalfacts и другим PR не
помогает. После итогового дерева PR пакет: только архитектурные контракты и
глобальные инварианты; обычные исходники убрать (доступны деревом); в промпт —
требование читать непосредственных callers, callees и тесты изменённого кода.
Контекст помогает найти правила системы, а не заменяет файловую навигацию.

## P2 — усилить схему результата (`review-kit-verdict-schema-v2`)

Для каждой находки: `severity`, `title`, `file`, `line`, `scenario`,
`observed_result`, `expected_result`, `evidence: [{file, line, reason}]`,
`confidence`. Блокируют только blocker/major с `confidence: high` и
заполненными `scenario`, `observed_result`, `evidence`. Это не гарантирует
истинность, но резко усложняет убедительную гипотезу без проверки.

## P2 — большие PR отдельно (`review-kit-large-pr-mode`)

До ~20–30 изменённых файлов и лимита дифа — один прогон; крупнее — группировка
по подсистемам, затем короткий финальный прогон межмодульных взаимодействий.
Generated-файлы, lock-файлы и snapshots не ревьюировать как обычный код, но
проверять согласованность с источником. Диф не обрезать молча: превышение
лимита — явный infrastructure failure либо chunked mode.

## P2 — измеримый eval (`review-kit-eval-harness`)

До дальнейшей настройки: 10–20 прошлых PR (несколько с реальными дефектами,
несколько чистых, несколько крупных межмодульных), зафиксировать ожидаемые
находки и известные ложные срабатывания. Метрики: precision блокирующих
находок; recall известных major/blocker; ложные блокировки на PR; доля находок
без проверенного evidence; стоимость и длительность. Для merge-гейта precision
важнее количества: цель — почти нулевая ложная блокировка, даже ценой
некоторого падения recall.

## P3 — модель только по eval (`review-kit-model-selection`)

Не исходить заранее из того, что reasoning-модель лучше Codex-модели для ревью:
нужны одновременно навигация по репозиторию, понимание кода, построение
сценариев отказа и дисциплина инструментов. Одинаковый eval минимум на двух
моделях × двух уровнях reasoning. Пины модели и CLI остаются, но меняются по
результатам измерения, а не по рассуждению в комментарии workflow.

## Минимальный набор, если делать только самое важное

1. CI на `build-prompt.sh` и `apply-threshold.sh` (сделано).
2. Read-only итоговое дерево PR при инструкциях из base.
3. Исправленные определения blocker/major.
4. Проверяемый evidence для каждой блокирующей находки.
5. Короткий промпт.
6. Прогон нового варианта на архиве PR, сравнение precision.

Основной прирост качества ожидается от пунктов 2–4.
