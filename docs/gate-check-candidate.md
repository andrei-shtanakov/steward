# `gate-check --candidate` — prospective-режим по кандидатной ревизии

Публичный способ прогнать gate-check по **содержимому каталога**, которое ещё не
является git-ref'ом: файлы правлены, но не закоммичены; бандл собран конвейером,
который ещё не решил, коммитить ли вообще. Заведён по steward#140 (входящий от
devtools, behaviour-конвейер, шаг S4).

```sh
uv run gate-check --profile team --candidate path/to/spec
uv run gate-check --profile team --candidate path/to/spec --format json
uv run gate-check --profile team --candidate path/to/spec --trace-matrix
```

Каталог **не обязан** лежать внутри чекаута: prospective-прогон не спрашивает у
git ничего. Коды выхода прежние — `0` чисто, `1` есть error-находки, `2` ошибка
конфигурации.

## Что проверяется и что нет

| Проверяется | Не проверяется (объявляется) |
|---|---|
| `GC-META`, `GC-STAGE`, `GC-DUP` | `GC-GIT-BRANCH` |
| `GC-COMPLETENESS`, `GC-TRACE`, `GC-TRACE-EMPTY` | `GC-GIT-ROLE` |
| `GC-UPSTREAM`, `GC-COMPILE` | `GC-APPROVAL-MISSING` |
| `GC-STALE`, `GC-STALE-UNPINNED`, `GC-STALE-KEY` | `GC-ARCH-CONFORMANCE` — **только клауза D9** (self-freshness) |
| `GC-BEH-*`, `GC-CHECK-*` | |
| `GC-ARCH-SCHEMA`, `GC-ARCH-EVIDENCE` | |
| `GC-ARCH-CONFORMANCE` — всё, кроме D9 | |

Про `GC-ARCH-CONFORMANCE` отдельно: гейт почти целиком выводится из байтов —
наличие отчёта, разбор JSON, схема, совпадение `manifest.sha256`,
`snapshot.complete`, политика findings/verdicts/unknown, возраст снапшота. Историю
читает ровно одна клауза (D9 self-freshness), и подавляется только она. Пропускать
гейт целиком значило бы спрятать весь этот класс ошибок за строкой «не проверено»
— тот же fail-open, только в приличном костюме (находка ревью-гейта на этом PR).

Правая колонка — не «прошло»: она **печатается каждым прогоном на stderr**, во
всех трёх ветках вывода (текст, JSON, `--trace-matrix`). Машиночитаемая копия
едет в JSON-пейлоаде ключом `not_evaluated` с причиной на гейт. Разделение
каналов держит на stdout ровно один разбираемый пейлоад, а объявление всё равно
доходит до человека; молча опускать ref-зависимые гейты значило бы красить
неизвестность зелёным.

Канон списка — `steward.gatecheck.candidate.NOT_EVALUATED`; тест сверяет каждый
`gate_id` с каталогом гейтов, чтобы переименованный гейт не превратил объявление в
мёртвую строку. Квалификатор частично пропущенного гейта живёт отдельным полем
`scope`, а не внутри id — иначе объявление стало бы непроверяемым ровно в тот
момент, когда стало точным.

## Почему это режим, а не ещё один адаптер фактов

Вопросы к git делятся надвое, и одним адаптером честно не закрываются.

**Вопросы к содержимому.** `blob_hash` — это git-адрес байтов файла
(`sha1("blob <len>\0" + bytes)`), чистая функция от содержимого: ни ref, ни
индекс, ни бинарь `git` для неё не нужны. На ней стоит stale-каскад, поэтому
кандидатная ревизия проверяется по пинам **до** коммита — и точнее, чем живой
прогон: тот читает `HEAD:<путь>` и сравнивает пины с последним коммитом, а не с
файлами, которые перед ним.

**Вопросы к истории.** `on_default_branch`, `is_ancestor`, `changed_paths_since`,
`merge_provenance` спрашивают, где содержимое стоит в истории. У кандидата ответ
не «нет», а «ещё не спрашивается». Вернуть `False` значило бы выдумать ответ — и
выдумать дорого: `check_status_git` выдал бы `GC-GIT-BRANCH` на каждый
`status: approved` артефакт бандла. Поэтому `CandidateGitFacts` на эти методы
**бросает** `FactsError`, а режим не запускает проверки, которые до них дотянутся.

`approvals` — единственный метод, который ни выдумывает, ни бросает: `None` в
протоколе уже значит «авторитетного источника нет», что здесь ровно правда.

## Конфликтующие флаги

Отвергаются кодом `2`, а не игнорируются молча: у каждого смысл есть только
применительно к закоммиченной ревизии, а проигнорированный `--approval-facts`
снаружи читался бы как «evidence посмотрели и оно в порядке».

| Флаг | Причина отказа |
|---|---|
| `--no-fs` | два разных источника фактов |
| `--emit-verdicts` | вердиктам нужна живая git-provenance (HEAD + dirty state) |
| `--approval-facts` | merge-evidence ключуется по merge SHA; кандидат не смержен |
| `--stage release` | release читает merge-evidence, которого у кандидата нет |

`profiles/arch-policy.yaml`, наоборот, **требуется** — как и в любом другом
режиме, и только когда бандл несёт `intended-graph.yaml`. Prospective-прогон
исполняет `GC-ARCH-CONFORMANCE` (без клаузы D9, см. выше), а политика — его вход;
без файла прогон отказывает кодом 2. Ранняя версия этого режима гейт пропускала и
политику не читала — довод «файл не нужен» относился к той, снятой, конструкции.

## Форма вывода

stdout — ровно один пейлоад: находки текстом, находки JSON'ом либо матрица.
Объявление `не проверено` идёт на stderr (см. выше). `--format json` всегда несёт
`mode` (`live` | `injected` | `candidate`) — чтобы потребитель не выводил из
собственных флагов, что именно покрыл код выхода.
`not_evaluated` печатается **только** в prospective-режиме: список описывает
режим, а не прогон, и пустой список на ref-режиме читался бы как «всё остальное
отработало» — утверждение, которого gate-check не делает (гейт может быть
неприменим к бандлу и без всякого git: нет arch-манифеста, стадия authoring).

```json
{
  "mode": "candidate",
  "findings": [],
  "errors": 0,
  "warnings": 0,
  "not_evaluated": [
    {"gate": "GC-GIT-BRANCH", "scope": "", "reason": "…"},
    {"gate": "GC-ARCH-CONFORMANCE", "scope": "D9 self-freshness", "reason": "…"}
  ]
}
```

## Для потребителей, ушедших на internal API

devtools до этого режима звал три пиненых символа напрямую
(`checks.collect_bundle`, `behaviour.check_behaviour_spec`,
`trace_matrix.build_trace_matrix`). Все три покрываются CLI: первые два — обычным
прогоном `--candidate`, третий — `--candidate --trace-matrix`. Прогон через CLI
шире: он добавляет резолюцию ролей, `GC-COMPILE` и весь stale-каскад, которых
обход не давал, и перестаёт зависеть от внутренней структуры пакета.
