# `steward adoption-scan` — pre-adoption скан внешнего инструмента

Детерминированная проверка чекаута внешнего инструмента/репо **до первого
запуска или импорта** (steward#104, from ai-repos-research). Происхождение —
живой инцидент 2026-08-23: клонированный репозиторий нёс fileless-загрузчик с
hardcoded C2 и триггером на верхнем уровне модуля — сработал бы при первом
`import`.

## Использование

```sh
uv run steward adoption-scan <путь-к-чекауту>
```

Сканируются только `*.py` (AST, без импорта и исполнения чего-либо из цели);
symlink'и не разыменовываются, `.git`/`__pycache__`/`.venv` и т.п. пропускаются.

## Три проверки

| Код | Что ловит |
|---|---|
| `SCAN-TOPLEVEL-EFFECT` | исполнимый при импорте код: statements верхнего уровня вне **тела** `if __name__ == "__main__"`; `if`/`try` рекурсируются теми же правилами (`try: import` fallback и `if TYPE_CHECKING:` — чистые), неопознанная конструкция флагуется (fail-closed); условие любого top-level `if` вычисляется при импорте — вызов в нём флагуется; `else`-ветка main-guard — ровно случай импорта, сканируется как обычный блок; **заголовки `def`/`class`** (декораторы, значения по умолчанию, bases, metaclass-keywords) исполняются при определении — вызовы в них флагуются; **тело class** исполняется при импорте целиком и рекурсируется теми же правилами (тела функций — нет) |
| `SCAN-NET-LITERAL` | hardcoded сетевые адреса в строковых литералах кода: URL-схемы (http/https/ws/wss/ftp) и валидные IPv4; докстринги исключены (ссылки в документации — не endpoint'ы), конфиги вне области по построению (сканируются только `.py`) |
| `SCAN-DYNAMIC-EXEC` | `exec`/`eval`/`compile` над нелитеральным аргументом; если модуль при этом импортирует сетевые модули (`requests`, `urllib`, `socket`, …) — находка называет это явно (форма инцидента) |

Задокументированные ограничения (обе — тот же размен «шум против сигнала»):
вызовы внутри top-level присваиваний (`logger = logging.getLogger(__name__)`)
не флагуются — иначе сигнал утонул бы в шуме, форма инцидента (голый
вызов-statement) ловится; аннотации не сканируются — под
`from __future__ import annotations` они не вычисляются вовсе, а
typing-конструкции завалили бы вывод.

## Трёхзначный вердикт

«Не сканировалось» **не эквивалентно** «чисто» (образец трёхзначного вердикта —
procoder `no-silent-green`):

- `clean` — каждый файл распарсен и просканирован, находок нет;
- `failed` — есть хотя бы одна находка (нечитаемые файлы репортятся рядом);
- `not_checked` — находок нет, но ничего и не доказано: часть файлов не
  распарсилась, каталог не обходится (права/то же I/O), либо в дереве вообще
  нет Python-файлов.

Exit-коды зеркалят gate-check: `0` clean; `1` failed **или** not_checked (оба
блокируют adoption без человеческих глаз); `2` config error (цель отсутствует /
не каталог). На stdout — байт-стабильный JSON (`verdict`, `findings[]`,
`scanned[]`, `not_checked[]`).

Скан — детектор для глаз, не автоматический вердикт о зловредности: находка
означает «не подключать, пока человек не посмотрел», а не «это малварь».
